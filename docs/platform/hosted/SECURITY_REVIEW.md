# Hosted platform security review and phase gates

Review date: 2026-10-19. Independent security reconnaissance; this is a design review, not certification or implementation signoff. The master plan was read in full. The hosted model supplements the existing single-origin SDK model; existing chain protocol and SDK behavior remain the compatibility boundary.

## Evidence and decisions

Inspected `packages/pact-sdk/src/server-auth.ts`, `server.ts`, `server-chain.ts`, `internal/auth-topology.ts`, the existing platform security/authentication docs, release contract, technical-debt register, dependency review and pinned runtime policy.

- Existing `createWalletAuth` verifies native Ed25519 signatures over server-retained exact UTF-8 challenge bytes with canonical public addresses and bounded random identifiers. Reuse the cryptographic approach, not its in-memory Maps or same-origin session semantics. The process-local store deliberately rejects known distributed/serverless environments and invalidates sessions on restart.
- `createPlatformReader` is already exported from `@pact/sdk/server`; use a persistent instance, never a reader created per access request. Its endpoint history, bounded pool and fresh snapshots are security state. `createPactApiHandler` deliberately shares history between separate public/protected reader pools. A second hosted reader must retain the same stale/backwards/frozen-chain protections. Database persistence does not establish reader-history safety across replicas or restarts.
- The existing release contract correctly preserves deactivation semantics: inactive offers deny new purchases but existing unexpired licenses remain valid. New resource registration requires an active verified offer; access checking must not accidentally implement on-chain revocation.
- Recommended pilot login is an explicitly **custom backend-mediated signed challenge and one-time grant protocol**, not an OAuth/OIDC/SSO provider. This avoids unsubstantiated interoperability claims. No refresh tokens, third-party cookies, global wallet bearer identity or browser-held grant. Broad federation remains deferred.

The protocol still requires a confidential app backend, app-authenticated login initiation/code exchange, exact registered callback, transaction-specific S256 PKCE, server-session-bound state, fixed issuer binding and atomic database redemption. PACT must not treat a random public app ID as client authentication. Generate a random launch identifier server-side; do not accept an arbitrary redirect destination on completion. Only the short-lived single-use code and state may cross the callback. Set no-store, no-referrer and frame-ancestors protections; render no third-party analytics on callback/login pages. Local loopback is a clearly marked development exception, with exact port/path registration.

## Required trust and storage boundaries

1. **Admin**: PACT-origin wallet proof establishes the developer account. Distinct purpose, wallet, origin/issuer, app/environment (where applicable), Devnet genesis/program, nonce, issue/expiry and action payload bind every proof. Never reuse buyer proofs for admin actions. Bind signed sensitive actions to the exact resource/configuration being changed; broad session recency alone is weaker than deliberate authorization. Recovery is manual and owner-controlled until separately designed.
2. **Backend key**: high-entropy random secret with a non-secret lookup prefix; HMAC-SHA-256 verifier using separately supplied server pepper is appropriate for random 256-bit tokens. Compare fixed-length verifiers using constant-time comparison. Persist creator/scopes/environment/expiry/revocation and last-used metadata. Return secret once with no-store; metadata-only subsequent lists. Revoke/rotate transactionally and support overlap. A key never proves control of a supplied wallet.
3. **Buyer**: exact server-stored wallet challenge, app/env and launch binding, one-time nonce consumption before returning success. Bind code to app/env, exact callback, PKCE challenge and issuer. Authenticate backend exchange; atomically transition unredeemed/unexpired code to redeemed in the same transaction that creates the grant. At most one success across independently competing DB connections. Store opaque grant hashes, not plaintext grants; grants remain in the customer server session. Revalidate app/key/grant/policy after awaited chain work before ALLOW so revocation during a slow read cannot produce a late positive result.
4. **Policy**: derive app/env from authenticated key and account owner from authenticated admin. Enforce owner constraints in every query/mutation; composite app/environment foreign keys prevent cross-tenant attachment. Resource keys select registered immutable bindings, never arbitrary caller offers/wallets/programs. Deny unknown JSON fields and unsafe string/URL sizes.
5. **Callback**: no wildcards, fragments, userinfo, unexpected query parameters, alternate-scheme URLs or normalization equivalence. HTTPS domain verification should use DNS TXT or an operator-supplied audited resolver; never fetch a submitted callback/metadata URL. Ownership verification must expire/recheck for domain change; new callback verification never implicitly approves old codes. Browser origins and callbacks are separate exact registries.
6. **Enforcement**: authenticated app + valid server-held wallet grant + active registered policy + fresh verified entitlement are all required. RPC/DB/schema/time uncertainty denies. ALLOW is a point-in-time decision, not legal title, durable transaction atomicity or proof a license remains valid. Safe buyer links must preserve existing metadata/checkout requirements.

Admission limits must bound active requests, pending queues, body bytes/time, DB pool size/statement time, public/auth/protected budgets, key/app/IP attempt rates and persistent record quotas. Rate limiting happens before expensive crypto/DB/RPC where possible; shared DB counters must be atomic if cross-worker guarantees are claimed. Do not trust X-Forwarded-For/Host/Proto without explicit trusted-proxy configuration. Secret-bearing backend endpoints reject browser-origin requests rather than offering permissive CORS.

## Primary guidance checked

[RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html) informs exact callbacks, state/PKCE, code injection and replay defenses. Applying those defenses does not itself make a custom service OAuth compliant. [OWASP API Security Top 10](https://api-security.owasp.org/editions/2023/en/0x11-t10/) informs object/property authorization, abuse budgets, SSRF, inventory and unsafe upstream handling. [Solana authentication guidance](https://solana.com/docs/frontend/messages-and-auth) supports server-retained exact challenges, single-use nonces and explicit non-transaction signing. Raw signMessage fallback should be labeled accurately; do not claim SIWS implementation without parsing/format verification and tests.

The official [Node announcement](https://nodejs.org/en/blog/vulnerability/october-2026-security-releases) was checked on 2026-10-19 and identifies the October 21 security release. Keep `scripts/validation/runtime.json`'s **2026-10-21** review gate; the current 24.22.0 pin is not clearance for the announced issue. Existing dependency exceptions expire **2026-11-15** and must be reassessed earlier for new packages/reachable parser, UUID or native paths. New database/auth dependencies require their own reviewed graph and must not silently inherit existing exception fingerprints.

## Phase 0 ADR disposition

Reviewed `ADR.md` on 2026-10-19. **PASS for Phase 0 architecture**: separate persistent service/SQL model, limited custom login, app-scoped opaque grants, exact callback and domain proof, owner tenancy, fresh reader reuse, post-read revocation validation and restore invalidation satisfy the design boundary. This approval authorizes proceeding to local implementation under the user's existing scope, not hosted rollout or authentication implementation signoff.

Freeze these details before shared action-proof code: mutation body `{payload, proof: {challengeId, signatureBase64}}`; challenge body `{action, appId, payload}`; signed proof binds the exact admin session incarnation, wallet, action, app (or explicit no-app context), environment and canonical schema-validated payload digest. Mutation verifies that same binding and consumes the proof in its mutation transaction. Canonicalization must define absent/null, key ordering, array ordering and bounded numeric values consistently; either reject duplicate input members or operate exclusively on the same strict normalized payload used to generate the proof. Browser challenge/verify needs an explicit browser binding/CSRF mechanism alongside exact Origin; a generic admin login session alone is insufficient for action-proof replay separation.

Implementation signoff: **pending**. This file records requirements and inspected evidence, not claims that new hosted behavior exists.

## Phase 3 connect protocol and gateway review

## Phase 4 hosted authorization review

**PASS — local Phase 4 security gate.** Inspected `access.mjs`, `telemetry.mjs`, the revised service/DB admission, migration `005_access_observability.sql`, runtime response contract and tests. Independently executed the service access tests: **3 passed**. QA's fixture independently encodes raw chain accounts and uses the actual SDK reader; its tests are separate execution evidence rather than synthetic reader tests relabeled as chain validation.

Access derives app from the authenticated key, wallet from its own app/environment/epoch-bound grant and offer from the enabled server resource. Strict bodies reject caller wallet/app/offer/program/network substitutions. No positive entitlement cache exists. After RPC, a protected SQL transaction locks and rechecks owner, app, credential, grant and resource/version/epoch. Final synchronous checks after transaction completion enforce key/grant expiry and original read/progress/chain/wall expiry bounds immediately before ALLOW. Response freshness includes the original read start/receipt/progress and a hard deadline; `verifiedAt` does not create a new eight-second budget. Offer deactivation preserves existing unexpired entitlements. Safe existing marketplace links explicitly require the seller's exact metadata and never imply checkout submission equals permission.

The review found and verified correction of a positive-response deadline that initially omitted key/grant expiry. `freshness.validUntilMs` now also caps the principal lease, preventing a delayed consumer from treating a fresh chain snapshot as valid identity after the grant/key expires. Separately, QA reproduced HTTP admission slots retained after incomplete-request sockets closed. Cleanup now releases idle aborted requests idempotently, retains leases while real handler work remains, and rejects a request already aborted before its handler starts. The PostgreSQL transaction adapter also destroys a connection if rollback fails, rather than returning uncertain transactional state to the pool.

Actual default limits: HTTP access/auth/control lanes **16/8/8**, no application queue; one lifetime SDK reader with shared history; non-access/protected chain work **2/6**, at most **2** protected reads per app; endpoint quarantine prevents new non-access reads accumulating after uncooperative transport timeouts. App/key access handler admission is **4 each**. Native PostgreSQL uses separate **2-connection control and protected pools** with **12 admitted operations per lane** by default. Access IP/route, app and key counters use the protected DB lane; app/key budgets are **120/60 per minute**, alongside the default **120 per IP/route**. No separate per-resource ceiling is claimed. Per-resource abuse policy and broader retention/operations work remain Phase 7 tasks. PGlite shares one local engine and does not establish physical SQL-pool isolation.

Telemetry queues at most **8** bounded jobs on the control lane. Collector errors are caught and observations may lag/drop; no telemetry database operation is awaited before returning authorization, and logging does not reset freshness or turn a denial into permission. Events retain fixed reasons/request IDs and owner scope, omitting grants, keys, signatures, wallets and provider errors. Readiness verifies exact migration names/checksums plus fresh SDK genesis/Clock/executable-program evidence; it is not entitlement, deployment-byte or authority-custody proof.

The independent final suite verifies late key/grant revocation, app pause, policy rebind and owner disable during RPC; malformed/wrong-owner/program/genesis/Clock/buyer evidence; backward/frozen history; exact expiry; delayed final SQL; protected capacity under HTTP/SQL saturation; abort cleanup; app fairness; quota rejection before chain work; telemetry failure and principal lease deadlines. The contract distinguishes typed expected DENY decisions from common authentication/precondition error envelopes; clients must deny both categories and unsupported/malformed responses.

No unresolved consequential Phase 4 defect remains in the reviewed local scope. Durable cross-restart clock rollback protection remains an explicit Phase 7 requirement. Phase 7 must also verify explicit slow-body and total-handler deadlines: Fastify's `requestTimeout` bounds receipt rather than all handler execution, and Node's connection-check interval can delay its enforcement.
