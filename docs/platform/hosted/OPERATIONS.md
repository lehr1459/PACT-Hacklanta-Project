# Private Devnet pilot operations

This runbook prepares owner-approved staging. It does not authorize deployment, external database changes, publication, wallet transactions or live infrastructure work. Assign a named operator, incident contact, provider, private RPC, secret manager, domain/TLS and privacy/recovery policy before opening ingress. The old public site and customer-hosted SDK remain independent rollback options.

## Supported topology and startup

Use the pinned reviewed runtime, one supervised persistent Node process, loopback-only API listener, fixed same-origin HTTPS gateway, PostgreSQL with encrypted transport, synchronous durable commits and a private persistent local clock directory. No hidden workers, replicas, shared/network clock volume or serverless runtime. Runtime and migration roles should be separate; clock storage, SQL and backups need accepted durability, ACLs, encryption and access controls. Read [clock decisions](CLOCK_ADR.md). Configure environment through the approved secret manager; `.env.example` contains names only. Never put an API key, grant, pepper or private RPC in browser variables or command-line arguments.

Start with ingress disabled. Validate configuration and migration checksums using the service CLI; inspect forward SQL before applying with separate migration authority. Do not edit applied migrations. Migration 006 changes the hosted auth epoch and resets nonlocal domain proofs. After starting, `/v1/health/live` checks process liveness; `/v1/health/ready` checks schema and actual SDK chain readiness. Readiness is not an entitlement, custody or production-security audit. Verify exact issuer, Devnet genesis/program, fixed gateway and no upstream bypass before opening traffic.

The gateway/operator must suppress raw authentication URLs, headers, bodies and callback codes in access logs, analytics and error capture. The API disables request logging. Browser test receipts contain fixed titles/status only; automatic screenshots/traces/video and raw errors are disabled. Approved screenshots are taken before proof material exists. Do not upload clock files, SQL backups, private evidence, raw artifacts or `.env` files. Six earlier proof-review screenshots were quarantined locally; textual scanning never established their raster contents safe.

## Capacity and monitoring

Current fixed pilot limits: HTTP 32 admitted work slots (16 access/8 auth/8 control), sockets 128, headers/receiving idle 5 s, handler 7 s, body 16 KiB. Complete-body handlers retain their absolute deadline; receiving idle cannot preempt their structured denial. Timed-out work retains admission until it actually settles. SQL control/protected lanes each have 2 connections and 12 total admissions, including running queries; query 3 s/statement 2.5 s/connect 1.5 s. Chain lanes reserve 6 access and 2 control slots, with 2 per app; timed-out/quarantined underlying work retains capacity. Key/app access has 4 in-flight slots and 60/120 requests per minute; route/IP 120/min is loopback-aggregate behind this gateway. A separately reviewed perimeter trusted-IP policy is required before public ingress; forwarded headers are not trusted by this service.

Persistent admission limits: 1000 developer accounts, 20 apps/account, 10 callbacks/app, 50 resources/app and 1000 resources globally; 10 active keys/app and 1000 credential metadata rows/app. Resource history normal caps are 1000/resource and 10000 global. An actual enabled-to-disabled containment transition may append one emergency row at capacity; repeating an already-disabled action does not grow history. Starting from compliant state, history is at most 1001/resource and 11000 global before any separate archive design. Inspect counts before importing/restoring data: existing excess is preserved, never automatically pruned. Re-enable/rebind/new binding and credential rotation fail closed at capacity; revoke/disable remain available. Existing account authentication remains available at the account cap. These are application limits, not a substitute for provider disk quotas, backup sizing or load acceptance. The intended pilot is 1–3 approved developers.

Usage responses return newest records within a 96 KiB budget; older retained SQL rows may be omitted. This is not a complete 30-day export. Monitor fixed request IDs, denial/error classes, queue saturation, readiness, RPC/DB faults, clock failures, credential age and DNS renewal. No raw secret-bearing proof should enter alerts. Alert delivery/contact integration is an owner decision; no unsolicited messages are sent by this code. Measure p50/p95/p99 and failure rates under the approved load before accepting capacity; do not widen freshness limits to meet a target.

## Retention and deletion

The checked-in operator command is `npm --prefix services/pact-api run maintain -- retention`. It defaults to dry run and never loads environment files, starts HTTP, migrates or creates a clock. Supply configuration using the approved environment/secret manager. Inspect bounded candidate counts first, then use `--apply --batch 100` only on an authorized database. Each table/lineage operation affects at most the chosen1–1000rows; repeat scheduled batches while `more` is true and monitor backlog. There is no automatic scheduler. Expired proofs/sessions/grants/login transactions are retained one extra day; usage 30 days, audit 90 days, expired/revoked credential metadata 90 days and budget windows 2 minutes. Current grants and immutable resource history remain. Aged rotation lineage is unlinked before removing expired ancestor metadata; valid descendants survive. Backups may retain data longer. Owner/legal approval is required for external retention, backup schedules, disclosures and incident holds.

For account containment use `maintain -- quarantine --account <public-account-id>` dry run; apply additionally requires `--confirm-wallet <public-wallet> --apply`. This disables owner authority while preserving evidence. Account erasure uses `maintain -- delete --account <public-account-id>` dry run. Apply requires prior quarantine, exact wallet confirmation and `--ingress-quiesced`: stop and drain **all** API/auth ingress and processes before invoking it. That flag is an operator assertion, not automatic proof. Public challenges have no account foreign key and in-flight authentication could recreate an account if ingress remains alive. Erasure is transactional and bounded to 10000 actual owned rows; larger records or foreign provenance dependencies roll back and require a separately reviewed offline batch plan. Another owner's data, global clock bindings, backups and public chain records are not erased. No legal erasure/compliance guarantee is made. Future wallet registration is a new action.

## Incident and recovery drills

For suspected key theft, quarantine the owner or pause the app, revoke affected keys/grants, preserve redacted audit evidence and require signed replacement credentials. An app key alone never proves wallet control. For callback/domain compromise revoke the callback, pause app login, reprove DNS and reauthenticate. For RPC/DB/clock uncertainty close or retain denied protected access; customer backends must never substitute a browser boolean or stale positive result. A timed-out mutation may have an uncertain COMMIT acknowledgement: inspect owned state before obtaining a new action proof, never blindly retry it. Verify containment with both prior credentials and fresh unauthenticated requests before reopening.

For process restart stop ingress, gracefully drain work and stop the owner. Preserve its private clock directory and SQL binding. Retry only after trusted wall time exceeds the saved ceiling. For abrupt crash a stale owner lock may remain. Prove the prior supervisor/process/host cannot still write, preserve a private copy of the lock, then move only that lock out of the directory. Keep `authority.bin` and SQL bindings untouched. Missing/mismatched authority, corrupt files or uncertain host time are incidents; do not reset them to bypass refusal. Recover with a new epoch instead.

For backup restore: keep ingress closed and all API/auth processes drained; restore SQL into an isolated new database, never over the live database. Verify trusted time, schema checksums and recovery point. Review and run [restore-quarantine.sql](../../../services/pact-api/operations/restore-quarantine.sql) with a scoped operator role. It pauses apps, invalidates restored bearer authority/proofs and resets nonlocal callback verification while preserving resource history/audit/clock bindings. Statements have lock/time limits; failure rolls back and requires review. Use a **new random pepper from the approved secret manager and a new empty private clock directory** before any service listener starts. Preserve old clock state privately, never copy it into the new directory. Reauthenticate owners, reprove callbacks, reissue credentials, deliberately reactivate apps and validate fresh buyer grants. Verify old keys, grants, codes, cookies and pending proofs deny. A same-secret snapshot can revive later-revoked credentials; recovery must not rely on automatic backup-rollback detection.

Rollback disables hosted ingress and returns users to the unchanged self-hosted integration option. Preserve SQL, clock evidence and purchase journals; schema recovery is roll-forward or isolated restore plus rekey, never destructive down-migration over live state. It cannot reverse finalized settlement or retract delivered content. Rehearse all steps on disposable local/approved staging data; actual provider recovery, on-call response, human wallet/device flows and pilot go/no-go remain owner gates.
