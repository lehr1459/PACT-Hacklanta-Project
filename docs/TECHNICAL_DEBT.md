# Post-MVP technical debt

Audit date: 2026-10-16. These are follow-up items, not permission for broad refactoring or deployment. No new critical defect was verified by this cleanup; that is not a production-security conclusion. Existing dependency vulnerability notes require a separate security review.

| Priority | Location | Issue and origin | Recommended future architecture | Risk / ordering |
| --- | --- | --- | --- | --- |
| High | `packages/pact-sdk/src/server-auth.ts`, `server.ts` | Authentication challenges, sessions and rate limits are process-local, deliberately built for one persistent development server. Known serverless runtimes are disabled. | Introduce an explicitly reviewed shared store with atomic single-use challenge consumption, expiry, sessions and distributed rate limits. Preserve fail-closed runtime guards until supported. | Replay/session consistency across workers; required before distributed authenticated deployment. |
| High | `web/lib/solana/{protocol,rpc,transaction}.ts`, SDK `index.ts`, `checkout.ts`, `server-chain.ts` | Binary validation and transaction rules are repeated across independently developed marketplace and SDK interfaces. | Establish independent parity fixtures against `solana/wire-spec.json`, then consider a versioned internal protocol module without changing public exports. | Drift can change licensing or transactions; consolidate only with coverage of all wire/ownership/freshness boundaries. |
| High | Web dependency tree; `web/README.md` dependency-audit notes | Prior wallet-adapter integration documented transitive audit findings; this pass did not perform a fresh vulnerability or runtime-reachability audit. | Dedicated pinned-dependency security assessment and staged, compatible updates with all wallet/browser checks. | Potential security exposure needs triage; no unrelated upgrades or speculative overrides in cleanup. |
| Medium | `packages/pact-sdk/src/server-chain.ts` | A wrapped RPC transport captures raw JSON to recover offer details from the validated root verifier. This avoided duplicate reads but couples transport and validation. | Internal validated snapshot result carrying offer and entitlement details, preserving the root public API. | Requires concurrency, timeout, same-slot and parity coverage before replacement. |
| Medium | `web/lib/platform/api.ts`, platform example configuration | Local origin/ports are defaults appropriate to the current persistent development server. | Require explicit canonical origin for hosted authenticated configurations, alongside the shared auth design. | Origin/session binding must remain exact; do before hosted auth support. |
| Medium | `qa/*/prepare*.mjs`, overlay/acceptance runners | Historical reproduction scripts pin revisions, timestamps, copied dependencies and prior failure directories. Some intentionally patch candidate sources. | Parameterized current-checkout runner with explicit package ownership, logs and fixture modes; retain the meaningful tests. | Running historical patch tools against current source may replay obsolete edits; current commands are documented separately. |
| Medium | `examples/pact-checkout-vanilla/tests/build-saturday-consumer.mjs`, `qa/hacklanta-final/` | Compatibility coverage depends on an unrelated Saturday Lights checkout and/or archived candidates. | Reviewed portable compatibility fixture or explicitly provided read-only consumer path. | Reproduction is workstation-dependent. Do not modify that repository as part of PACT cleanup. |
| Medium | Package installation and browser configurations | Several packages and tests resolve sibling `node_modules`; SDK build order and one-at-a-time web builds are manual. | Deliberate workspace/test orchestration with lockfile and public package isolation review. | Improper deduplication can duplicate React or change SDK consumer resolution. |
| Medium | Root/web example offers and deployment guides | Fixed Devnet offers and historic deployment statements support reproducible demos, but their live state can change. | Explicit example configuration and separately maintained operator deployment evidence. | Do not infer active license, deployed program status or current authority from a historical report. |
| Low | SDK/server and fixture scripts | Dense single-line code reflects fast implementation and obscures reviews. | Small formatting-only follow-ups with behavior-preservation review. | Large formatting churn would hide meaningful cleanup changes. |
| Low | `docs/STATUS.md`, `HANDOFF.md`, historical milestone reports | Cumulative historical records mix states and stale preview PIDs. | Maintain the current documentation index; archive/reorganize only after checking incoming links. | Historical evidence is useful; old instructions must not supersede current requests. |
| Low | Root `.env.example` versus `web/.env.example` | Earlier Base-only template remains alongside the active dual-chain web template. | Keep scopes explicit in onboarding; retire the root template only after confirming external tooling no longer uses it. | Uncertain external consumption; preserved in this pass. |

Resolved during this pass: obsolete Base-first scaffold onboarding, generator installation instructions tied to one workstation, the platform example's missing Playwright config selection, and linked-contract build resolution. See [cleanup results](POST_MVP_CLEANUP.md).
